## 2. What it stands on, VERIFIED 2026-09-27

- **Numpad keys are lost in egui, not in winit.** winit 0.30.13 reports every key with its
  physical code on every OS, numpad keys distinct: `KeyCode::Numpad0`-`Numpad9`
  (`winit-0.30.13/src/keyboard.rs:493-511`), macOS's keypad codes mapped to them
  (`platform_impl/macos/event.rs:573`). egui's adapter folds them into the digits:
  `KeyCode::Digit0 | KeyCode::Numpad0 => Key::Num0` (the fork's `egui-winit/src/lib.rs:1542`;
  paths into egui below are the fork's, under its `crates/`).
- **Stock eframe shows an app no winit event.** `App`'s one input hook is
  `raw_input_hook`, after the fold. The author's fork adds the missing layer for the numpad
  (`eframe/src/native/wgpu_integration.rs:934-970`, `NumpadCaptureMode`,
  `eframe/src/epi.rs:651-700`), with NumLock inferred from each key and macOS
  given an always-capture mode. VellumFE pins the fork at
  `2e2ead359c474102c5f713f86f2ec4a3be5e741b` (branch `numpad-support`, egui 0.35.0,
  `rust-version = "1.92"`, under this workspace's 1.96.1).
- **NumLock, per OS.** Windows: `GetKeyState` at any time, an `unsafe` call not used
  (§6 item 5). Linux (X11 and Wayland): winit
  tracks it (`platform_impl/linux/common/xkb/state.rs:133`) and does not expose it; its
  `ModifiersState` has four flags (`keyboard.rs:1693`). Inferred from each numpad key, it
  is exact for a keybind, which is decided on the key itself; only a NumLock indicator
  before any numpad key is pressed is out of reach on Linux. macOS has no NumLock; the
  key in its place is Clear, reported as `KeyCode::NumLock` (`keyboard.rs:520-523`), so
  Hydra keeps its own numpad mode there, toggled by Clear.
- **Several native windows, one process.** egui 0.35's `show_viewport_deferred` and
  `show_viewport_immediate` (`egui/src/context.rs:3960`, `:4014`); VellumFE already
  uses them for detached windows (`reference/VellumFE/src/frontend/gui/app/detached.rs:317`).
- **The focus rule.** After each frame, when nothing holds focus and no key capture is
  armed, focus goes to the command input
  (`reference/VellumFE/src/frontend/gui/app.rs:3426-3438`).
- **Double-clicked on Windows.** A console program gets a console window of its own.
  VellumFE stays a console program and lets the console go when it is its only process,
  so a terminal launch keeps its terminal
  (`reference/VellumFE/src/main.rs:906-917`).
- **Progress bars today.** VellumFE draws horizontal bars with a skin-art overlay frame and
  four text formats, all inside the bar
  (`reference/VellumFE/src/frontend/gui/app/widgets/vitals.rs:12`, `:22`, `:127-160`). No
  vertical fill: the word does not occur in that file.
- **CI.** The workspace builds and tests on Ubuntu and Windows
  (`.github/workflows/ci.yml:21`); macOS runs only the iOS core build (`:86`).
- **The web hub's requests** are `Add`, `Remove`, `Reconnect` and `Shutdown`
  (`crates/cena-web/src/server.rs:99`), answered by the session table's owner
  (`crates/cena/src/play.rs`).

## 3. The first build: the live run's cockpit

Everything the M6 live run needs, and nothing more.

**The hub**, what the binary opens with no arguments or on a double-click:

- Tabs: **Live** and **Closed** (§1 row 7).
- A card per character: vitals, roundtime, room, group, connection state.
- Start from the roster with a saved password, quit, reconnect, open a headless
  character's window, shut everyone down.
- The merged thoughts, speech, logons, deaths and announcements (R4; `crates/cena-ui/src/merge.rs`).

**A play window per character:**

- The story, painted by the triggers (M8).
- One command input; a click nothing consumed returns focus to it; `;to` and `;all`
  reach the others.
- Vitals, roundtime and cast time, hands, and the room: exits, creatures with their
  status, players painted by the triggers.
- Connection state and retries.
- Hydra's own messages (hunt, loot, heal) in their own pane, not in the game's text.
- Stop, for this character.
- Panes that drag, resize and snap to the grid, the layout saved by character name
  (`SessionId` restarts at 0 every run, `plan/23` §D1a).
- Closing it leaves the character running headless.
- The numpad, through the fork's hook.

**Later:** the launcher tabs Lich's launcher has (saved logins, manual login, accounts,
game and instance); drawers, opacity, click-through; themes, skins, fonts, settings
editors; the map (in Despana meanwhile), creature field, injury doll, effects, gamepad;
progress bars as §1 row 8 describes them (step 10); Despana's full port.

**Open, Claude's recommendation: a hunt panel** -- its step, its target, and why it is
waiting (*"resting: mana 30%, wants 50%"*). The hunt reports only as text today, so it
needs a status event from the hunt. It is what makes a stuck live run readable. Step 8,
last, so it blocks nothing.

## 4. Where it sits

- **A new crate, `cena-gui`,** depending on `cena-ui` and `cena-session` (`plan/28` §7b's
  third option). Not on `cena-host`, not on `cena-web`. The binary depends on it. The row
  is already written down, commented, in `crates/cena-arch-tests/tests/layering.rs:74`:
  *"cena-tui/gui/web (cena-ui, cena-session) -- and never each other"*. `ALLOWED_EDGES` is a
  set equality with the real graph, so the row goes live in the commit that adds the
  crate (step 1), not before it.
- **Desktop only.** It is not one of the five core crates the mobile builds check
  (`plan/12` §1a).
- **Threads.** eframe needs the main thread; the tokio runtime is built by hand on worker
  threads, and the sessions run there. The binary still decides when sessions start and
  stop.
- **Control.** The hub asks what the web hub asks. With two frontends asking it,
  `HubRequest` moves down into `cena-ui` rather than being copied.
- **Data.** One task per character hands the GUI the latest snapshot and the new lines,
  and wakes it (`egui::Context::request_repaint`), as Despana's pump does
  (`crates/cena-web/src/presentation.rs`); what both need moves down, not across. The GUI
  draws from `GameState` directly.
- **Keys.** The fork's numpad hook, widened to every key (step 7). The change lands in the
  fork (`github.com/Nisugi/egui`), which is a push to the author's repository: the author
  makes it or approves it. Until then the fork's `NumpadCaptureMode` as it is.
- **Testing without running the binary.** `egui_kittest` (in the fork, with its `wgpu` and
  `snapshot` features) drives the GUI headless and renders images a test compares and a
  reviewer can look at. A preview example drives it from the scripted game
  (`AnsweringSource`) and a committed capture.
